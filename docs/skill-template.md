# Skill 编写模板与规范

新 skill 一律从这份骨架出发：先过「硬性约束」，再抄「骨架」，最后按工种挂「附加模块」，发布前过「质检五问」。

## 硬性约束（违反 = 不合规）

| 项 | 要求 |
|---|---|
| frontmatter | `name`、`description` 必填；其余字段非必要不加 |
| name | 小写 kebab-case，≤64 字符，必须与目录名一致 |
| description | ≤1024 字符，第三人称；必须写清「何时用」（含触发词）和「何时不用」—— 这是唯一常驻 AI 上下文的行，像防火墙规则一样写边界 |
| 正文 | ≤500 行；超了就把细节下沉到 `references/` |
| 语言 | 正文全中文；name、目录名、文件名英文 |
| 链接 | 一律相对路径 |
| 引用链 | 只允许一层（SKILL.md → references/），不得链式再引 |
| references 体积 | 单文件超过 100 行须在开头加目录 |
| 跨工具字段白名单 | frontmatter 只用规范字段（name、description、license、compatibility、metadata、allowed-tools）；Claude Code 专有字段（如 disable-model-invocation）会让 claude.ai / Skills API 打包硬报错 |
| 脚本 | 默认不写；写则零依赖、失效时指令能兜底、放 `scripts/` |

## 骨架（所有 skill 共用）

````markdown
---
name: my-skill            # = 目录名
description: <这是什么。何时用：具体场景 + 触发词。何时不用：边界。>
---

# My Skill

<一段话：身份 —— 这个 skill 是什么、为谁服务、明确不做什么。>

## 前置条件

<什么必须成立才能开始。每条不满足时：回什么话、停。
没有前置条件就整节删掉。>

## 铁律

1. <绝不做的事。>
2. <必须做的事。>

<祈使句，一条一个约束，不写理由 —— 理由放 docs/SPEC.md。>

## 流程

1. <步骤。细节下沉 references/ 并在此处链接。>

## 深入

- [references/xxx.md](references/xxx.md) — <什么时机才需要读它>

## 输出物

<skill 在消费方项目里创建/依赖的文件与目录。
纯对话型 skill 整节删掉。>
````

## 工种附加模块

### 流程纪律型 —— 约束 agent 行为的时机与边界

bug-corpus 是这型。重心：**前置条件**（时机闸门，不满足就停）+ **铁律**（停止条件与禁止项）。骨架不加节，写厚这两节即可。

### 工具包裹型 —— 包住脚本 / 第三方 API

- **Scripts 表格**：脚本 × 用途 × 前置（如需登录），有多个脚本时必须用表
- **Verified status**：对外部世界的每个论断带验证日期 —— 包裹的东西会腐烂，日期让腐烂可见
- **Maintenance**：漂移了怎么发现（self-test / 冒烟命令）、怎么修
- **ask-before-X**：动用户凭据、cookie、会话之前，先问用户

### 混合型

两种模块按需叠加，骨架不变。

## 质检五问（发布前过一遍）

1. 只读 `description`，模型能在**对的时机**选中它、**错的时机**放过它吗？
2. 正文每一句是在**命令 AI**，还是在**向人解释**？解释性的挪去 README / docs/SPEC.md
3. AI 照流程走到每一步，有歧义的分支吗？
4. 前置条件不满足时，AI 知道停在哪、回什么话吗？
5. 删掉任意一节会不会更差？不会就删 —— 短是美德，每一行都在花调用时的上下文
